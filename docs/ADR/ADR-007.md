# ADR-007 · S-07 · Chiến lược Output Caching + Redis Store & Eviction Tags
- Trạng thái: Đã chốt
- Người viết: TV4
- Liên quan: C-03, C-04 · FR-RCP-001, FR-CAT-001, NFR-PERF-001, NFR-PERF-002 · CR-07

## Bối cảnh
SRS v1.0.0 tồn tại 4 cơ chế cache chồng chéo (IMemoryCache, Redis Cache-Aside, Output Cache, Next.js ISR) với TTL không đồng nhất từ 5 đến 65 phút. Nguy hiểm hơn, response của GET API công khai bị cache tĩnh hoàn toàn, khiến người dùng vô danh (Guest) có nguy cơ nhìn thấy bài viết nháp (Draft) của Tác giả (lỗi C-03).

## Quyết định
Phương án chuẩn hóa qua ASP.NET Core Output Caching với Redis Backing Store & Eviction Tags:
- Phân định Ranh giới Caching:
  - GET /api/v1/categories: TTL = 30 phút, Tag = categories.
  - GET /api/v1/recipes: TTL = 5 phút, Tag = recipes. Chỉ cache response chỉ chứa bài Status == Published.
  - GET /api/v1/recipes/{slug}: TTL = 5 phút, Tag = recipes, recipe:{slug}.
  - GET /api/v1/recipes/search: TTL = 1 phút.
  - Bỏ qua Output Cache (Bypass Cache) 100% đối với các request chứa header Authorization: Bearer ... và các endpoint cá nhân (GET /me/recipes, GET /recipes/id/{id}).
- Eviction theo Tag: Khai báo interface ICacheInvalidator tại Application. Khi có thao tác mutation (Tạo/Sửa/Xóa/Publish/Unpublish/Archive), Handler gọi EvictByTagAsync("recipes") hoặc EvictByTagAsync("categories") để xóa sạch cache tương ứng trên Redis ngay lập tức.

## Hệ quả
- Tốc độ phản hồi cho Guest đạt p50 <= 150ms.
- Triệt tiêu hoàn toàn nguy cơ lộ bài Draft cho Guest.
- Phụ thuộc Redis server (nếu Redis down, fallback sang In-Memory/DB và ghi log Degraded).

## Phương án dự phòng
Nếu Redis ngắt kết nối, OutputCache tự động fallback về Memory Cache nội bộ của từng API instance hoặc đọc trực tiếp PostgreSQL mà không đánh sập ứng dụng.
